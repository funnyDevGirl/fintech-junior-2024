### CRUD Пользователей:
1) POST /api/v1/users - создание пользователя/регистрация
- При регистрации всем пользователям устанавливается Role 'USER'.
2) GET /api/v1/users/{id} - получение пользователя по идентификатору
3) PUT /api/v1/users/{id} - обновление пользователя
4) DELETE /api/v1/users/{id} - удаление пользователя
5) POST /api/v1/users/password-reset - запрос сброса пароля
- Ожидает POST-запрос с email пользователя в теле запроса.
- Вызывает метод requestPasswordReset из сервиса для отправки кода подтверждения на указанный email.
- В классе User реализованы методы сохранения кода подтверждения и проверки его актуальности.
6) PUT /api/v1/users/password-reset - сброс и смена пароля
- Ожидает PUT-запрос с новым паролем и кодом подтверждения в теле запроса.
- Вызывает метод resetPassword, который проверяет код подтверждения и обновляет пароль.

### Аутентификация и авторизация
1) POST /api/v1/auth/login - аутентификация пользователя
- Пример запроса:
```
{
  "username": "chuck.norris@google.com",
  "password": "some-password",
  "rememberMe": true
  }
```

```

- Во время логина система будет формировать JWT-токен, который вернется клиенту.
- После чего каждый запрос пользователя к приложению будет содержать этот токен, и таким образом приложение сможет определить, от кого пришёл запрос.
- В теле запроса можно установить опцию "запомнить меня", в таком случае токен будет сгенерирован на срок 30 дней.
- Если опция не отмечена (false), по умолчанию токен будет выдан на срок 10 минут.
- Если в запросе переданы некорректные данные или пользователь не найден, вернется ответ со статусом 401.
- Доступ к маршруту аутентификации доступен всем пользователям, все остальные - только для аутенцифицированных.
- При попытке совершить операцию, на которую у пользователя нет прав (например, удаление и редактирование другого пользователя), возвращается ответ со статусом 403.
#### Настройка процесса аутентификации:
- Для аутентификации пользователя используются его email и passwordDigest - специальный хэш, связанный с паролем.
- Класс EncodersConfig содержит механизм хеширования пароля (BCrypt), а также механизмы, отвечающие за создание, декодирование и проверку JWT.
- Для работы JwtEncoder нужны RSA-ключи — их можно сгенерировать, выполнив в терминале команды:
```
openssl genpkey -out private.pem -algorithm RSA -pkeyopt rsa_keygen_bits:2048
openssl rsa -in private.pem -pubout -out public.pem
```
- Для удобства тестирования добавлены сгенерированные ключи (в реальных проектах доступ к приватному ключу должен быть ограничен):
```
# application.yml 
rsa:
  private-key: classpath:certs/private.pem
  public-key: classpath:certs/public.pem
```
- Для аутентификации реализован метод loadUserByUsername() в сервисе CustomUserDetailsService, реализующем интерфейс UserDetailsManager.
- Генерация JWT-токена реализована в классе JWTUtils
2) /api/v1/auth/logout - эндпоинт для logout
- Так как используется JWT, состояние сессии управляется на стороне клиента, а не на сервере, т.е. вызов logout обычно просто подразумевает удаление токена на стороне клиента.
- logout настроен в методе securityFilterChain() в Spring Security, он сбрасывает информацию о сессии, а также возвращает успешный ответ.
